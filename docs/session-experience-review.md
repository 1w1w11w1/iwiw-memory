# 会话体验审视：架构不足及其在 chat 中的具体后果

> 方法：通读 chat.py 当前实现（462 行），模拟真实用户会话流程（开场→说话→回指→长对话→管理→异常），
> 每个架构不足都翻译成"用户此刻会看到什么"。不动代码，只审视。

## 严重度 A：信任伤害（说了却没记住 / 刚记住就忘）

### A1. 助手会做出"虚假承诺"——说记住了，实际没写

BASE_SYSTEM_PROMPT 规则 3 要求助手"主动提示用户这些内容已（或建议）写入记忆"。但助手没有任何写入工具，
写入只发生在 should_trigger 命中时。两者不对齐：

```
你> 我下周三想去听一场爵士演出
助手> 好的，这个安排我帮你记下来了。        ← 助手承诺了
（但"想去听演出"不命中 triggers 词表 → 无提取 → 无写入）

你>（三句话之后）我周三那天有什么安排来着？
助手> 抱歉，你没有跟我提过周三的安排。        ← 用户信任崩塌
```

根因：提示词让助手承诺一个它没有的能力；触发词表（triggers.py）覆盖不了自然语言的计划/意愿表达。
后果等级：**最高**。记忆系统的核心承诺就是"我说的你会记住"，虚假承诺一次，用户就回到手动记录。

### A2. 会话中新增的 core 记忆与词面索引不刷新——刚写入的信息下一句就"忘"

chat.py:335 `always_load = _always_load_text()` 和 chat.py:342 `session.build_word_index(...)`
都只在启动时计算一次，之后不更新：

```
你> 记住，我对芒果过敏。            ← 触发提取，写入 core 记忆成功
助手> 好的，芒果过敏我记住了。
你> 那给我推荐个果汁？
助手> 推荐芒果汁怎么样？           ← always_load 是启动时的旧快照，不含新 core 记忆
```

同理，`build_word_index` 不刷新 → 新写入的记忆**永远无法被本轮会话的回指联想命中**
（"那个过敏的事"→ SessionState 词面索引里没有新记忆）。
后果：**同一会话内刚写入的关键信息，注入与联想双通道都看不见**，重启才能生效。

### A3. 提取无对话上下文 → 产出"孤儿记忆"

chat.py:370 `extract_and_save(line)` 只传当前一句，不传 history（extractor 的 context 参数存在但没用上）：

```
你>（聊了五轮两个方案的利弊）
你> 行，那就定第二个方案吧。        ← should_trigger 命中"定"→ 提取
（提取器只看到"行，那就定第二个方案吧"，不知道两个方案是什么）
→ 入库记忆："用户决定选第二个方案"   ← 孤儿记忆，之后注入也无法理解
```

后果：记忆库被无法理解的碎片污染，之后注入这些记忆时助手引用得莫名其妙。

## 严重度 B：卡顿与信息损失

### B1. 高信号消息同步阻塞 5–15 秒

chat.py:370 提取是 `await extract_and_save(line)`——一次 LLM 调用串行执行在回复之前。
后果：用户说完一句重要的话，界面卡住十几秒才开始回复（还叠加流式首 token 延迟）。
体感像死机。应异步化（后台提取，回复先行）。

### B2. LLM 回复失败时，用户消息不进 history

chat.py:448-450 回复失败 `continue`，此时 history.append 还没执行（在 452 行）——
用户那句话**从上下文里消失**：

```
你>（说了很长一段）→ 网络超时，回复失败
你> 刚才说的你再看看？
助手> 你还没说过什么。             ← 用户消息没进 history
```
后果：一次网络抖动 = 用户重打一整段话。

### B3. DSC 压缩丢弃原文，且无持久化——早期细节永久不可回溯

压缩时 `history = history[-keep:]`，早期原文从内存**永久消失**；检查点只含话题/决策/任务，
不含具体内容；整个会话也没有 rollout 持久化（对比 Codex 的 rollout.jsonl）。
后果：
- 用户第 5 轮讲的长故事（提取器只存了要点），第 30 轮问细节 → 无处可查；
- 意外退出（崩溃/断电）→ 整场对话除已提取记忆外全部丢失。
这与"超大上下文记忆系统"的定位直接冲突。

### B4. compacted 检查点固化不更新

压缩触发时生成一次检查点文本，之后每轮原样注入（chat.py:419-420），直到下次压缩（再过 12 轮）。
但 session.update 每轮都在更新话题/决策——检查点却不反映：
后果：第 13 轮说的新决策，在 13–24 轮期间只存在于单条消息里，滑出窗口后丢失
（SessionState 内部有，但模型看不到；联想能召回记忆本身，但"用户做过这个决定"的状态对模型不可见）。
修复方向明确：render_checkpoint() 是确定性的、零成本，应该每轮重渲染。

## 严重度 C：质量退化（慢性）

| # | 不足 | chat 后果 |
|---|---|---|
| C1 | 规则触发漏报（"我想要 Switch"/"我要去上海"不在词表） | 信息静默丢失，用户以为记住了 |
| C2 | 回指候选误带：SessionState"最近/高频"策略在密集回指时给出错误记忆 | 助手张冠李戴（聊饮食时插一句"你马拉松时注意饮食"） |
| C3 | 同话题重复注入：4 轮窗口一过，同一记忆重新注入 | 长聊同一话题时助手反复提同一件事，像个复读机 |
| C4 | /mem search 走相关性阈值：低分相关的记忆被滤掉 | 用户明明有这条记忆却搜不到，以为丢了 |
| C5 | /extract 只取"最近一条"消息 | 想补救提取三句前的话时，提取的是最近的闲聊 |
| C6 | 无使用强化/衰减执行：touch_memory 无调用方，priority 不随使用进化 | 几个月后旧记忆挤占注入预算，新记忆被挤出 top-3 |

## 按体验伤害排序的修复优先级

| 优先 | 修复 | 对应 | 一句话理由 |
|---|---|---|---|
| 1 | 提示词与能力对齐（去掉虚假承诺）+ 触发词表放宽 | A1/C1 | 信任是记忆系统的生死线 |
| 2 | 会话内状态一致性：always_load / word_index 每轮或按事件刷新 | A2 | "刚说的下一句就忘"不可接受 |
| 3 | 提取带上下文 + 异步化 | A3/B1 | 一次修复两个体验问题 |
| 4 | compacted 每轮重渲染 + 回复失败也记 history | B2/B4 | 小改，消除信息黑洞 |
| 5 | 会话持久化（rollout 文件）+ 压缩重注入 | B3/G5 | 对齐"超大上下文"定位，工程量较大 |
| 6 | 使用强化（G1）+ 检索管理命令不走阈值 | C4/C6 | 长期质量 |

> 审视结论：当前最痛的问题不在"检索不够聪明"，而在**写入与状态一致性**（说了没记住/刚记就忘/承诺不兑现）。
> 这与"注意力成本"讨论的判断一致：先把状态一致性做对，联想/压缩的价值才能真正被用户感知。

## 验证补记（实测，2026-09）

> 上文审视原为代码走读推演。按"理论自洽不等于有效"规则，已对每条主张补实测。结果：**10 条主张 8 条坐实、1 条被推翻（自我修正）、1 条部分修正**。

| 主张 | 判定 | 实测证据 |
|---|---|---|
| A1 触发漏报 → 无写入 → 虚假承诺 | **坐实** | 端到端管道："我下周三想去听一场爵士演出"无提取提示、/stats 记忆总数 0；下一轮追问时模型仍说"这件事我帮你记着"——承诺与库状态矛盾；会话结束即跨会话丢失 |
| C1 触发词表覆盖率 | **坐实，比预期严重** | 10 句自然语句仅 2 句触发（漏 80%）："我对芒果过敏""我把烟戒了""我妈让我周末回家吃饭""我给自己定了个存钱目标"全部漏掉 |
| A2 会话内写入盲区 | **坐实（范围修正）** | 精确复现组装路径：无词面（"推荐个果汁"）与有词面（"芒果汁能喝吗"）两场景注入均不含新 core 记忆——core_slugs 每轮排除 + always_load 快照陈旧**双失效**，词面重叠也救不了。缓解：12 轮窗口内用户原话在 history 可见。精确后果 = 窗口滑出后（13+ 轮）彻底盲 |
| B1 提取同步阻塞 | **坐实** | 实测单次提取 9.0s（无上下文）/ 10.9s（带上下文），发生在回复之前 |
| B4 compacted 检查点固化 | **坐实** | 探针：render_checkpoint 随状态变化（新决策进入检查点），chat 固化压缩时旧版 → 新决策对模型不可见直到下次压缩 |
| C2 回指候选误带 | 坐实 | 长对话评估 turn 78：期望 food-spicy，注入含 hobby-piano/ref-feedback 等无关记忆 |
| C6 touch_memory 无调用方 | 坐实 | grep 全库 0 调用方 |
| B2/B3/C5 | 坐实（代码路径事实） | append 位于 try 之后；无会话落盘；last_user_message 仅存最后一条 |
| A3 孤儿记忆污染 | **部分推翻** | 实测无上下文提取"行，那就定第二个方案吧"返回（无）——extractor 足够保守，未产生垃圾记忆。修正后的真实问题：9s LLM 调用白花 + 该记的事实没记（信息丢失而非污染） |
| C4 阈值滤掉搜索结果 | **推翻（自我修正）** | 实测 FTS 命中分数 1.08 远高于阈值 0.15，阈值过滤实际不会滤掉任何命中。从修复清单移除 |

### 附带发现

验证过程中在真实库发现一条**来源不明**的遗留记忆（food-drink-preferences，内容为咖啡/香菜偏好——本会话从未讨论过）。来源虽不可考，但它恰好实证了 G1/G2（使用驱动整理 + 周期卫生审查）的必要性：**没有自动审查，连"库里有一条谁也没说过的记忆"都不会被发现**。

### 修正后的修复优先级（与原表差异：移除 C4，其余维持）

1. A1/C1：提示词与能力对齐 + 触发机制重做（词表 20% 覆盖率不可接受——改为每轮轻量 LLM 判定或放宽规则）
2. A2：会话内状态一致性（always_load/word_index 按写入事件刷新；新 core 记忆不进 core_slugs 排除集或即时并入常驻）
3. A3+B1：提取带 history 上下文 + 异步化（消灭 9s 阻塞与信息丢失）
4. B4：compacted 每轮重渲染（零成本）
5. B3：会话持久化（rollout）；C 级维持原判断

## E2E 红基线（tests/e2e_chat_eval.py，已建立）

chat 体验已固化为可重复的 E2E 套件：subprocess 管道驱动真实 chat，每场景独立临时库（MEMORY_AGENT_DB_PATH 钩子），
硬判定只用确定性锚点（[提取]/[联想注入]（MEMORY_AGENT_ECHO_STATE=1 回显）/记忆总数/DB 内容/耗时）。

| 场景 | 基线 | 对应审视项 |
|---|---|---|
| trigger_coverage（3 句自然事实写入率） | **FAIL 0/3** | A1/C1 |
| inject_relevance（相关问句联想注入） | **PASS** | L2 联想正常 |
| extraction_context（铺垫后决策的提取质量） | **FAIL**（未触发+库空） | A3/B1 |
| latency（高信号 vs 闲聊轮均耗时差） | **FAIL Δ19.3s/轮** | B1 |
| commands / llm_failure | PASS | — |

用法：`python tests/e2e_chat_eval.py [场景名...]`（无参跑全部）。
**优化纪律**：每个修复以对应场景由红变绿验证，其余场景不得回退；LLM 回复质量不在硬判定内（输出全文供人工软审阅）。

### ⚠ latency 场景判定不可靠（标记）

两次全量运行 Δ 分别为 +28.7s 与 -4.5s —— LLM 端到端延迟方差（17~46s/轮）远大于提取信号（~9s），
整进程墙钟差无法稳定测量 B1。B1 的可靠证据是进程内直接计时（extract_and_save 实测 9.0/10.9s）。
该场景需重设计：改为在 chat 内对 extract 阶段单独计时并输出锚点，或从 E2E 移除、由进程内计时测试替代。
