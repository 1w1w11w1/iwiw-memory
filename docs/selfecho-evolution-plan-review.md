# SelfEcho 演变计划评审与修订建议

相关文档：

- `docs/agent-direction-decisions.md`：已经确认的智能体方向决策。
- `docs/agent-direction-questionnaire.md`：尚待确认的问题清单。
- `docs/project-renaming-notes.md`：项目重命名决策草案。

## 当前判断

SelfEcho 已经不再是“给旧记忆系统套一个控制台”的阶段。当前代码已经形成了新的中心：

- GUI 默认进入树洞对话。
- 原始 GUI 会话写入 `selfecho_data/sessions.db`。
- 会话整理可以生成滚动摘要，并触发长期记忆写入。
- Markdown 长期记忆仍是真源，继续保留 L0/L1/L2/L3 权重。
- 旧 Claude Code 历史已经变成可迁移、可搜索的背景资料，而不是产品边界。

但这里还需要进一步修正：SelfEcho 的长期目标不只是“树洞 + 记忆管理 GUI”，而是成为一个明确的个人智能体。树洞不是终点，也不应成为项目的全部身份；它本质上是一种对话策略，用来处理用户正在倾诉、需要被接住、需要被温和整理的场景。

项目真正的主轴应是：成熟的个人智能体工作流、harness、问题处理能力，以及支撑这些能力的强记忆管理系统。

因此，早期文档中“前三阶段不做聊天，只做记忆控制台”的路线已经过期；刚完成的“不要追求万能助手”的表述也需要重新校准。更合理的主线是：

> 以强记忆系统为底座，以对话模式识别为入口，逐步建设可观察、可测试、可回滚的 agent harness，让 SelfEcho 最终具备成熟的问题理解、规划、执行、纠错和追踪能力。

换句话说：不要过早做一个粗糙 Agent，但必须朝成熟 Agent 架构演进。

## 需要修订的旧叙事

### 1. 旧外部会话项目不应再作为架构中心

早期文档曾把外部会话历史项目当作第二记忆层，包括安装、MCP、hook、迁移指南。这与当前内化后的代码不一致。

修订方向：

- 对外只称“会话记忆层”“历史回放”“导入历史”。
- 旧外部会话项目已经从顶层目录移除。
- 旧数据库保存在 `selfecho_data/legacy/claude_code_history.db`，只作为 legacy 导入资料。
- `AGENTS.md` 应改写为 SelfEcho 原生会话记忆层，不再要求优先调用旧 MCP 工具。

### 2. Hook 不应继续定义记忆生命周期

旧计划里 hook 仍是自动写入和调试中心。当前目标已经转向 GUI 会话周期整理。

修订方向：

- Hook 保留为外部输入源或兼容通道。
- 新的主触发应是“会话结束 / 固定轮数 / token 阈值 / 手动整理”。
- 长期应将 hook 写入也收敛到统一 ingest 或整理队列，而不是直接各写各的。

### 3. GUI 不只是控制台，而是 SelfEcho 的默认体验

早期分析建议第一版不做聊天，但现在用户明确要求“树洞会话是核心默认页面”，并且前端已经实现。

修订方向：

- 对话页是主入口。
- 记忆页服务于纠错、回放、整理，不抢占聊天中心。
- 模型页服务于配置与测试，不暴露原始 JSON。
- Prompt 和健康状态不要恢复成顶级导航，可作为模型/系统的次级入口。

### 4. “树洞优先”不等于“不做智能体”

树洞策略是 SelfEcho 的一种交互策略，不是项目边界，也不应独占默认身份。

修订方向：

- 当用户只是表达痛苦、困惑、关系压力时，SelfEcho 先承接和整理。
- 当用户提出明确问题、计划、任务或需要决策支持时，SelfEcho 应进入问题处理模式。
- GUI 和 harness 需要明确区分“倾诉模式”和“问题处理模式”。
- 问题处理能力应由 harness 承担，而不是散落在 prompt 里。
- Agent 行为必须可解释、可暂停、可回滚，不能用“自主性”掩盖不可控。

### 5. 项目名称可能需要重新定位

如果项目继续叫 SelfEcho，它天然强调“回声、自我映照、倾听与记忆”。这适合树洞和长期记忆，但对“成熟个人智能体 / workflow harness / 问题处理系统”的表达不够完整。

重新命名应满足：

- 不把项目限定成树洞、日记或心理陪伴。
- 能容纳记忆、对话、计划、工具、工作流和 agent harness。
- 不显得像企业效率工具，也不显得像纯情绪陪伴产品。
- 保留“个人连续性”和“被理解”的气质。
- 名称最好短，便于作为目录名、API 前缀和 GUI 品牌。

在正式改名前，应先完成命名决策文档；不要直接全局替换。因为改名会影响：

- GUI 品牌文案。
- README 和架构文档。
- Python 包名、数据目录、配置目录。
- API title 和未来插件/服务名。
- 旧数据目录迁移策略。

## 修订后的目标架构

SelfEcho 应拆成六层，而不是简单的“前端 + API + 记忆”：

```text
web/                         # 默认交互界面：对话、记忆、模型、运行状态
selfecho_api/                 # HTTP API，负责鉴权边界、请求编排、静态服务
selfecho_agent/               # Agent harness：运行、计划、工具、状态、错误恢复
selfecho_session/             # 会话记忆层：原始消息、摘要、回放、检索、整理状态
memory_agent/ + memory/       # 长期事实记忆：Markdown 真源、搜索、编辑、审计
selfecho_config/              # 模型、prompt、策略、工具权限和运行配置
```

### Agent harness 应包含什么

Harness 不是“多写几个 prompt”。它至少应包含：

- `Run`：一次 agent 运行的结构化记录，包含 run_id、session_id、状态、开始结束时间。
- `Turn`：用户输入、模型输出、工具调用、错误、恢复动作的事件流。
- `ContextBuilder`：统一组装 L0/L1、滚动摘要、最近消息、相关检索结果、当前任务状态。
- `IntentRouter`：区分树洞承接、问题分析、计划制定、执行型任务、记忆维护。
- `DialogueMode`：把用户输入判定为倾诉、问题求解、计划推进、任务执行、记忆管理等模式。
- `Planner`：把复杂问题拆成步骤，但允许用户拒绝或修改。
- `ToolRegistry`：工具注册、权限、参数 schema、执行结果记录。
- `Executor`：执行工具、处理超时、重试、取消、失败降级。
- `PolicyGuard`：隐私、危险操作、记忆写入、外部副作用的确认边界。
- `Trace`：让 GUI 能看到 agent 为什么这样做、用了哪些上下文、改了什么。
- `Evaluator`：用固定案例回放测试回复策略、记忆整理和工具行为。

这套 harness 是后续问题处理能力成熟的关键。

## 建议的新阶段路线

### Phase A：收敛术语与文档

目标：让代码、文档、行为指令说同一种语言。

任务：

- 更新 `AGENTS.md`：用 SelfEcho 会话记忆层替代旧会话系统表述。
- 更新 `README.md`：补充当前 GUI 信息架构和会话周期整理规则。
- 用 `docs/legacy-history-import.md` 记录旧历史导入方式。
- 新增一份架构决策记录：为什么不再把旧会话系统作为产品概念。

完成标准：

- GUI、README、API 文档、行为指令中不再把旧项目名作为核心概念。
- 旧名称只出现在 legacy migration 语境中。

### Phase B：对话模式识别与会话生命周期

目标：让每次对话既有生命周期，也有明确模式；系统知道用户是在倾诉，还是需要解决问题。

任务：

- 增加 dialogue mode：venting、problem_solving、planning、execution、memory_management。
- 对话页可显示当前模式，但不要造成打扰。
- 用户可以手动切换模式，系统也可以给出温和建议。
- 增加“结束当前会话 / 稍后整理 / 立即整理”的明确动作。
- `sessions.db` 增加或稳定使用会话状态：active、ended、consolidating、consolidated。
- 自动整理从“每 12 条消息”扩展为可配置策略：轮数、时间、token、手动。
- 会话列表展示整理状态，而不只展示 turn 数。
- 对话页展示当前注入上下文摘要：L0/L1、滚动摘要、最近消息、相关检索结果。

完成标准：

- 用户能知道一段会话是否已经整理。
- 用户能知道系统当前是在倾听，还是在进入问题处理。
- 原始消息、周期摘要、滚动摘要之间关系可见。
- 整理不会让用户感觉系统在暗中改东西。

### Phase C：Agent harness 骨架

目标：先把 agent 运行变成结构化系统，再逐步增加工具能力。

任务：

- 新增 `selfecho_agent/` 模块。
- 定义 `AgentRun`、`AgentEvent`、`AgentState` 数据结构。
- 每次 GUI 对话消息都产生 run trace，而不是只有一段 assistant 文本。
- 增加 intent routing：venting、analysis、planning、action、memory。
- `ContextBuilder` 负责统一上下文注入，替代散落在 `_reply()` 中的拼接。
- GUI 对话页可折叠展示“本轮使用的上下文与策略”。
- 暂时只注册只读工具：搜索长期记忆、搜索会话、读取摘要、健康检查。

完成标准：

- SelfEcho 每次回答都有可追踪运行记录。
- 模型回复、上下文注入、工具结果不再混在不可观察的 prompt 中。
- 即使不执行外部副作用，也已经具备成熟 Agent 的运行骨架。

### Phase D：记忆整理进入可审阅闭环

目标：自动整理不直接变成黑箱写入。

任务：

- 整理结果先生成候选变更：create/update/append/merge/archive/delete。
- GUI 展示候选变更、理由和 diff。
- 允许用户接受、修改、拒绝候选。
- 自动写入仍可保留，但应在设置中明确，并有审计记录。
- 审计页进入记忆页二级导航，而不是隐藏在 API。

完成标准：

- 每次长期记忆变化都能回答：来源会话是什么，为什么改，改了哪里，如何回滚。
- `.history/`、审计记录、GUI diff 三者能互相对应。

### Phase E：问题处理能力

目标：让 SelfEcho 不只会聊天，还能处理用户提出的问题。

任务：

- 建立问题类型：
  - 情绪/关系承接。
  - 生活决策分析。
  - 学习/项目规划。
  - 信息整理。
  - 可执行任务。
- 为每类问题建立最小处理协议：澄清、建模、方案、风险、下一步。
- Planner 输出可编辑计划，不默认直接执行。
- 对不确定、涉及健康/关系/重大决策的问题保持边界。
- 对执行型任务建立确认机制和失败恢复策略。

完成标准：

- 用户提出复杂问题时，系统能稳定从“接住表达”过渡到“结构化处理”。
- 回答不是临时 prompt 风格，而是由 harness 的 intent 和 plan 机制支撑。

### Phase F：长期记忆 UI 从“文件编辑器”升级为“分级治理”

目标：保留 Markdown 可读性，同时降低外部观看时的生硬感。

任务：

- L0/L1/L2/L3 左侧列表继续保留，但右侧详情做成“摘要头 + 元数据 + 正文 + 历史”。
- 增加按 type、更新时间、是否有历史版本、是否来自会话整理筛选。
- 合并操作增加双栏预览：来源、目标、合并后。
- 删除、归档、降级、升级都走同一确认与审计流程。
- 增加“新建记忆”入口，但默认不鼓励频繁手写。

完成标准：

- 长期记忆从外部看不再像一堆 Markdown 文件，而像一套分级知识系统。
- 仍然不牺牲 `memory/*.md` 作为真源。

### Phase G：模型与 Prompt 管理服务 Agent 角色

目标：模型管理不是配置页堆字段，而是服务不同 agent 角色。

任务：

- Provider 模板继续保留：DeepSeek、OpenAI Compatible、OpenRouter、自定义。
- 增加模型角色绑定：树洞聊天、问题分析、规划、摘要、记忆整理、工具执行检查。
- Prompt 页面作为模型页次级入口：树洞回复、问题处理、规划、会话摘要、记忆整理、记忆编辑。
- Prompt preview 展示最终组装上下文，而不是只展示单个文件。
- 保留树洞回复策略优先，但将工作/问题处理规范沉淀为独立 agent policy。

完成标准：

- 用户能清楚知道“哪个模型负责聊天、分析、规划、整理记忆”。
- Prompt 编辑后能预览实际效果。

### Phase H：工具系统与外部动作

目标：在 harness 稳定后，再加入真正可执行的工具能力。

任务：

- 工具注册采用 schema + 权限 + 风险等级。
- 先做低风险本地工具：读取项目状态、搜索资料、生成文档草稿、整理会话。
- 对文件写入、删除、联网提交、外部账号操作等高风险动作强制确认。
- GUI 展示工具调用历史、参数、结果和错误。
- 支持取消、重试、回滚建议。

完成标准：

- SelfEcho 可以执行任务，但用户能看见它在做什么。
- 工具失败不会污染记忆或中断整个会话。

### Phase I：旧历史和外部输入源归档化

目标：兼容旧数据，但不让旧架构继续牵引新系统。

任务：

- 旧历史导入保持幂等。
- GUI 默认只显示 SelfEcho GUI 会话，旧历史在“导入历史”筛选中出现。
- 为旧历史增加只读标记，不参与新会话生命周期。
- 顶层旧外部项目目录已移除，仅保留导入数据库。
- 如果继续保留 Claude Code hook，让它调用 SelfEcho API 或共享写入层。

完成标准：

- 删除或移动旧目录不会影响 GUI 主路径。
- 旧历史只影响搜索背景，不决定新记忆架构。

## 当前最应该推进的 8 个具体任务

1. 修订 `AGENTS.md` 和旧 docs，消除旧架构作为主概念的描述。
2. 建立项目重命名决策文档，先定命名原则与候选，再决定是否全局改名。
3. 给会话增加模式识别、状态与“结束会话”动作，让整理从按钮变成生命周期。
4. 新增 `selfecho_agent/` harness 骨架：run、event、context builder、intent router。
5. 将 `_reply()` 从简单 prompt 拼接迁移到 agent run。
6. 把整理候选变更做成可审阅 diff，而不是只显示 JSON 结果。
7. 在记忆页加入审计/回滚二级入口。
8. 在模型页加入 Prompt 与模型角色绑定，不恢复为顶级导航。
9. 给关键路径补测试：dialogue mode、run trace、context builder、迁移幂等、整理不删原文、记忆编辑备份、GUI 默认页。

## 暂时不建议做的事

- 不要在 harness 尚未成型前引入完整 ReAct 工具循环。
- 不要用“自主智能体”绕过确认、审计、回滚和测试。
- 不要把 Markdown 记忆迁移成纯数据库。
- 不要把旧会话系统作为新产品名称继续暴露。
- 不要把 Prompt/健康/审计全部恢复成顶级导航。
- 不要为了“智能”让系统默认大批量自动合并、删除长期记忆。

## 修订后的北极星

项目的下一阶段不是停留在记忆控制台，也不是立刻膨胀成不可控的万能助手，而应追求：

> 一个以强记忆管理为底座、能区分倾诉与问题求解、由成熟 harness 驱动的问题处理型个人智能体。

它应该能倾听和记录，也能分析和行动；能先接住用户，再判断是否进入问题处理；能规划，也能停下来确认；能使用工具，也能解释和回滚；能整理记忆，但不把用户变成记忆管理员。
