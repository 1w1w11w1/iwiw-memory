# 上下文压缩与注入策略评估

> 评估基于当前代码（chat.py / config.py / retrieval.py / extractor.py / maintenance.py）。
>
> 一句话结论：**注入策略骨架完整（分层/预算/去重/联想/位置都到位），是当前做得较好的部分；压缩策略基本空白 —— 所有"压缩"实际都是"截断/丢弃"，没有真正的摘要/蒸馏机制。** 对"超大上下文记忆系统"的目标，压缩是当前最大短板。

## 1. 注入策略现状盘点

| 层 | 实现 | 注入位置 | 预算 | 去重 | 评估 |
|---|---|---|---|---|---|
| 常驻层（core） | _always_load_text()：core 记忆全文 | system | MEMORY_RECALL_MAX_CHARS=2500 字符截断 | 无（core 固定） | 骨架对；隐患是全文注入，core 增多时挤占预算且稀释注意力 |
| 联想层（话题检索） | _related_text()：search_memories top_k=3 + 主题轨迹 | system | 同上 2500 字符（与常驻各自独立，不共享总量） | 窗口 4 轮 | 联想机制已验证；缺口是无重排、预算不与常驻共享 |
| 会话历史层 | history[-(12*2):] 最近 24 条消息原文 | messages | 仅轮数限制，无字符预算 | — | 原文保留正确，但窗口外直接丢弃（无压缩） |
| 注入位置 | 常驻+联想进 system，历史进 messages | — | — | — | 正确：记忆当已知背景，历史当对话记录 |

### 注入策略评价

**做对的**：
- 分层注入（常驻/联想/历史）符合成熟四层模型。
- 注入进 system 层（模型当作已知背景自然引用，而非检索结果展示）。
- 联想机制（向量+主题轨迹+窗口去重）经真实对话验证有效。
- 有字符预算、有去重窗口、有注入精度收敛（top_k=3）。

**缺口**：
1. 常驻层全文注入，无常驻摘要；core 数量/篇幅增长即膨胀。
2. 预算单位是字符非 token；中文 token 约等于字符，但英文/代码偏差大。
3. 常驻与联想预算各自独立，不共享总量；总注入量可能超预期。
4. 联想无重排（cross-encoder），top-3 仍可能带无关噪声。
5. 会话历史层无预算，消息很长时历史可能吃掉大量上下文。

## 2. 压缩策略现状盘点

| 压缩机制 | 现状 | 说明 |
|---|---|---|
| 会话历史滚动摘要 | 无 | 只有 12 轮截断（窗口外丢弃 = 信息丢失，非压缩） |
| 常驻摘要（core 压缩） | 无 | core 全文注入，仅字符截断（截断不等于摘要） |
| 长期记忆合并去重 | 部分 | extractor 提取是会话到长期记忆的蒸馏；/maintain 只生成归档候选，不做内容合并压缩（merge 是手动命令） |
| 记忆引用（slug+摘要） | 无 | 上下文无引用式记忆呈现 |
| token 预算 | 部分 | 字符级、分层独立，无总量、无 token 计量 |

### 压缩策略评价

**这是当前最大的空白。** 所有"压缩"实际都是"截断/丢弃"：

- 会话超过 12 轮后，早期上下文直接消失（除非被提取进长期记忆）—— 对万字级长对话是致命短板。
- core 记忆没有摘要，注入成本随记忆量线性增长。
- 长期记忆库本身没有自动合并/摘要机制，碎片记忆会累积。

## 3. 与成熟做法的差距矩阵

| 能力 | 成熟做法 | 当前 | 差距 | 投入 |
|---|---|---|---|---|
| 会话历史压缩 | 滚动摘要：每 N 轮把窗口外原文压成 summary，上下文=最近原文+滚动摘要 | 12 轮截断丢弃 | 大 | 中（每 N 轮一次 LLM 调用） |
| 常驻记忆压缩 | 维护流程定期把 core 压成紧凑摘要，注入用摘要 | core 全文注入 | 中 | 中 |
| 长期记忆合并 | 自动识别重复/碎片记忆并合并 | 仅手动 merge | 中 | 中 |
| token 预算 | 按 token 计量、各层共享总量、超预算分层裁剪 | 字符级、分层独立 | 小 | 小 |
| 联想重排 | cross-encoder 精排 top-20 到 top-3 | 无 | 小 | 中（依赖+内存） |
| 记忆引用 | 上下文放 slug+摘要，细节按需取 | 无 | 中 | 小 |

## 4. 推荐优先级（按投入产出比）

| 优先级 | 项 | 理由 | 工作量 |
|---|---|---|---|
| P0 | 会话滚动摘要 | 万字对话刚需；当前早期信息全丢 | 中 |
| P1 | token 预算（总量共享 + token 近似计量） | 注入量可控的先决条件 | 小 |
| P2 | 常驻摘要（core 维护压缩） | 核心记忆膨胀隐患 | 中 |
| P3 | 联想重排 | 注入精度最后一块 | 中 |
| P4 | 记忆引用 | 记忆量大时的注入瘦身 | 小 |

> 原则：压缩（P0/P2）优先于注入精度（P3），因为先保证喂进去的信息不丢，再优化喂得精。
