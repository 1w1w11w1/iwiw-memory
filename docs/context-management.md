# 上下文注入与压缩管理

> 现状盘点 + 专业评估 + 成熟做法建议。
>
> 结论先行：当前方案的注入逻辑是正确的骨架，但存在**三个未接线参数**（已定义未使用）、**一个重复注入缺陷**、以及**整体缺少 token/字符预算与压缩机制**。

## 1. 当前上下文注入现状盘点

对话工作台（chat.py）每轮实际注入四部分：

| 成分 | 现状 | 注入时机 | 是否有预算控制 |
|---|---|---|---|
| 系统提示 | 固定文本 | 每轮 | 无（恒定小） |
| core 常驻记忆 | _always_load_text()：core 记忆全文 | 启动时组装，每轮随 system 注入 | 已接线：MEMORY_RECALL_MAX_CHARS 截断（本轮修复） |
| 话题检索记忆 | _related_text()：search_memories top_k=3 | 每轮 | 已接线：MEMORY_RECALL_MAX_CHARS 总量预算 + exclude_slugs 去重 |
| 会话历史 | 最近 12 轮原文 | 每轮 | 仅轮数限制，无摘要/压缩 |
|
提取链路（extractor.py）另有两处注入：

| 成分 | 现状 | 说明 |
|---|---|---|
| 相关记忆全文 | _related_memories_text()：检索 top_k=5 相关记忆全文 | 喂给提取模型做精准 update/去重 |
| 记忆目录 | _memory_catalog_text()：前 80 条 slug/desc | 防重复创建 |

### 现状问题清单

1. **两个已定义未使用的参数**（本轮已修复）：MEMORY_RECALL_MAX_CHARS（检索注入无字符预算）、format_memory_context()（chat 未用，自行拼装）。
2. **常驻与检索重复注入**（本轮已修复）：core 已注入的记忆，话题检索仍可能返回并重复注入（exclude_slugs 参数存在但 chat 未传）。
3. **常驻层无压缩**：core 记忆以全文注入，若 core 数量/篇幅增长会挤占预算；成熟做法是维护一份常驻摘要（core summary），而非全文。
4. **会话历史只有原文、无压缩**：12 轮窗口外全部丢失；成熟做法是滚动摘要（最近原文 + 更早的摘要）。
5. **每轮无差别检索**：即使纯闲聊也做检索；成熟做法是触发式检索（仅消息含明确话题/查询意图时）。
6. **检索无重排序**：search_memories 的加权融合分数未经 cross-encoder 重排；对个人记忆库（<1000 条）可接受，但大规模时需要。
7. ~~向量全表扫描~~：已随去向量化删除（search_vectors/embedding 均已移除）。

## 2. 成熟上下文注入做法（专业评估）

### 2.1 注入分层（记忆进入上下文的标准模型）

成熟系统把上下文分成四层，每层有独立预算：

```
┌─ 系统提示层（恒定小）─────────────────────────┐
├─ 常驻记忆层（必须载入，预算约 1-3k tokens）─────┤
│   不是核心记忆全文，而是维护过的紧凑摘要        │
├─ 主动检索层（按需，预算约 2-4k tokens）─────────┤
│   每轮按 query 检索 top-k，经重排、去重、预算裁剪 │
├─ 会话历史层──────────────────────────────────┤
│   最近 N 轮原文 + 更早的滚动摘要                │
└─────────────────────────────────────────────┘
```

关键原则：**常驻层必须极小且稳定**。模型对常驻内容的注意力是均分的，塞入过多常驻记忆会稀释注意力；应该只放身份、安全约束、以及高频引用的关键事实，且以摘要形式存在。

### 2.2 预算管理（最实用的第一步）

为每层分配硬预算（字符或 token），超预算按优先级裁剪：

- 常驻层：core 摘要总预算（如 2000 字符），每条按核心度截断；核心度低的 core 降为检索层。
- 检索层：top_k 上限 + 总字符预算 + 每条内容截断（如 250 字符摘要）。
- 历史层：窗口轮数 + 摘要轮数。
- 超预算时的裁剪顺序：先裁检索层摘要细节，再裁历史原文，最后才裁常驻。

### 2.3 检索触发与去重

- **触发式检索**：不是每轮都检索。当消息包含明确查询意图、提及记忆线索、或话题跨度大时才检索；闲聊/寒暄跳过，省一次嵌入与 LLM 调用。
- **常驻-检索去重**：检索时排除已注入的 core slug（本轮已实现 exclude_slugs）。
- **引用式检索**：上下文放 slug + 一行摘要，模型需要细节时再按需取全文（减少注入量，代价是可能多一轮工具调用）。

## 3. 自动上下文压缩的成熟方法

### 3.1 滚动摘要（rolling summary）—— 会话历史压缩的标准做法

```
每 N 轮：对窗口外旧消息生成摘要，叠加进 rolling summary
上下文 = 最近原文窗口（M 轮）+ rolling summary（更早的浓缩）
```

- 优点：保留全局脉络，成本线性，实现简单。
- 实现要点：摘要要与记忆提取解耦 —— 摘要是上下文管理，提取是长期记忆沉淀（本项目的 extractor 已独立承担后者）。

### 3.2 记忆蒸馏 / 关键点提取 —— 长期记忆的压缩

把会话沉淀为长期事实（本项目 extractor 已实现），并定期对 long 记忆做合并去重（维护流程）。常驻层维护一份核心摘要：由维护流程定期把 core 记忆压缩为紧凑摘要，注入时用摘要而非全文。

### 3.3 记忆引用（contextual references）

上下文不注入全文，而是注入 slug + 一句话摘要 + 关键字段。模型可基于摘要判断是否需要展开。适用于记忆量大的场景，把上下文占用从 O(全文) 降到 O(摘要)。

### 3.4 重要性评分裁剪

对注入候选按重要性打分（如 core > 近期访问 > 高相似度），预算不够时优先丢低分项。本项目已有 access_count/时间衰减信号可复用。

## 4. 性能与内存开销评估（你的权衡点）

| 开销项 | 现状 | 评估 | 建议 |
|---|---|---|---|
| 向量检索 | 全表扫描所有 chunk | <1000 条完全可接受（毫秒级）；>5000 条退化 | 引入 sqlite-vec 或 FAISS 索引；或 FTS 粗筛 → 向量精排 |
| 嵌入模型内存 | bge-small-zh 常驻（约 33MB 权重 + PyTorch 开销约 200MB） | 本地单进程可接受 | 已是懒加载单实例，勿多开 |
| 每轮嵌入调用 | 每条 query 一次 embed（CPU 约几十 ms） | 可接受 | 触发式检索可减少次数 |
| LLM 调用 | 每轮回复 + 高信号提取 | 提取是无差别的单次判断 | 批量提取（周期汇总）或仅在触发时提取，已实现触发式 |
| 注入 token | 常驻+检索+历史 | 无预算时随记忆量线性增长 | 预算管理 + 摘要（见 2.2） |
|

## 6. 联想优化实测（本轮）

新增两个可重复的评估脚本（均在 tests/ 下）：

- tests/associative_recall_eval.py — 联想质量离线评估：direct（直接关键词）/ semantic（语义近义）/ topic（对话主题联想，无关键词兜底）/ unrelated（无关反例），10 个用例。当前 10/10 通过。
- tests/long_conversation_eval.py + tests/_conversation_data.py — 万字级长对话评估：96 轮 / 10205 字符，8 主题埋点 + 长程回指，逐轮驱动真实注入管线，量化回指命中率、注入预算、长程联想。

### 本轮发现并修复的问题

1. session 永久去重导致联想枯竭：injected_slugs 无限累积，长会话后所有记忆都被排除，回指全部失联 → 改为窗口内去重（最近 4 轮）。
2. 去重窗口过大：注入只进 system（每轮重建），不驻留上下文；24 轮窗口把讨论期注入的记忆长期排除 → 窗口缩到 4。
3. 主题轨迹被 bigram/分句碎片污染：topic_freq 被无意义碎片占据，真主题词排不上 → 改为 2/3 字 n-gram + 多层过滤（停用词 / 首尾停用字 / 子串半词 / 实义核心数）。
4. 联想注入噪声：top_k=5 带出大量无关记忆，误注入还会挤占去重窗口阻塞后续回指 → top_k 收敛到 3。

### 当前基线（诚实）

- 单轮联想（直接/语义/主题/反例）：10/10 —— 联想质量达标。
- 万字长对话长程回指（纯指代式）：2/8（25%）—— 命中回指句含实义词的场景；纯指代回指（无关键词、无相邻线索）是当前机制的极限。

### 后续方向（提升长程纯指代回指）

1. 会话级记忆索引：维护会话中讨论过的话题档案（slug + 主题词 + 最后讨论轮次），回指时按档案召回，而不是全局词频。
2. LLM 指代消解兜底：12 轮窗口内的指代，模型从历史原文即可消解（注入非必需）；窗口外才需档案。
3. 重排：cross-encoder 精排提升注入精度（顺带减少噪声注入）。
