# 智能体方向决策记录

本文记录已经确认的产品与架构方向，用于约束后续设计。

## 1. 项目身份

项目目标是个人智能体，而不是纯树洞、纯记忆库或纯聊天工具。

它应同时具备两类能力：

- 帮助用户解决问题的能力：理解问题、澄清条件、建立计划、执行或辅助执行、追踪结果。
- 陪伴型 agent 能力：根据用户归档的长期记忆，总结并调整回复策略，让系统更理解用户的表达习惯、思考方式和情绪偏好。

## 2. 开源定位

项目应面向开源发布，目标用户不只是一名开发者本人。

因此后续设计需要考虑：

- 默认配置应尽量易用。
- 文档要能让没有 AI 工程背景的人理解。
- GUI 要降低概念负担。
- 模型、记忆、工作流和安全边界都需要清晰呈现。

## 3. 产品气质

项目应保持温柔、易用、开盖即食的印象。

它不应表现成只服务工程师的复杂控制台，也不应表现成纯情绪陪伴产品。更合适的方向是：

> 让完全不熟悉 AI 知识的文科生，也能上手使用智能体解决问题，逐步拥抱 AI 时代。

## 4. 智能体优先，而不是树洞优先

项目命名与产品定位更倾向智能体。

“树洞”不应成为项目主身份，而应作为对话策略的一种分支。未来系统需要明确区分：

- 工程模式：用户明确需要解决问题、推进任务、整理材料、规划执行。
- 非工程模式：用户更可能是在表达、探索、发散、寻求陪伴或需要被接住。

但界面不应直接把后者命名为“倾诉模式”，因为这会显得刻意、沉重，甚至让用户不自在。

## 5. 模式命名倾向

当前保留两个方向：

- `工作模式`：明确表示用户需要问题处理、计划、执行和工具能力。
- `陪我想想`：作为非工作模式的候选名称，比“倾诉模式”更含蓄，也更适合表达轻量陪伴、共同思考和情绪承接。

未来 GUI 可以用一个明确开关展示“工作模式”。当工作模式关闭时，系统不简单等同于倾诉，而是更倾向温和、陪伴、探索和承接。

## 6. 模式识别策略

模式选择应同时保留用户控制和智能判断：

- 前端提供用户偏好选项，类似 Codex 的计划模式、目标追求模式。
- 系统也可以根据上下文和用户语气进行判断。
- 二者需要权衡权重，而不是只有手动或只有自动。

这意味着后续 harness 应支持：

- 用户显式模式设置。
- LLM 或规则产生的模式判断。
- 最终模式决策及其理由记录。
- 用户随时覆盖系统判断。

## 7. 个性化回复策略

系统应利用用户长期记忆，总结用户偏好的回复策略。

这种策略不是固定 prompt，而应能根据场景调整。例如：

- 用户需要被接住时，先承接情绪。
- 用户需要清晰框架时，给边界和结构。
- 用户需要推进时，给可执行步骤。
- 必要时直接在对话中给出选项，例如：
  - “你希望我更犀利地反驳你一下，还是先针对你的困境给建议？”
  - “你现在更想让我陪你想想，还是切到工作模式一起拆解问题？”

这要求后续 agent harness 能把“用户偏好记忆”转化为“本轮回复策略”，而不是只把记忆原文塞进上下文。

## 8. 问题处理能力仍待 harness 决定

在工作模式下，系统应主动追问缺失条件、建立方案、拆解步骤。

但具体实施方式依赖 harness 设计，因此暂时不直接定死。后续应通过以下模块实现：

- intent routing
- context builder
- planner
- tool registry
- policy guard
- run trace

## 9. 情绪优先原则

当用户情绪很重但同时有明确问题时，优先接住情绪。

这是作者明确的产品倾向。系统不应把所有表达都快速转换成任务，也不应在高情绪状态下急着规划。

例子：

> 当用户说“我不活了”时，大概率可能不是严格意义上的自杀意图声明，而可能是一种情绪宣泄。

系统策略应是：

- 先接住情绪。
- 降低刺激和压迫感。
- 逐步引导用户表达具体处境。
- 视风险程度进行安全判断。
- 必要时引导用户寻求现实支持。

这里需要后续引入更专业的心理调节流程，并通过联网检索或文献资料补充设计依据。

## 10. 对后续研究的要求

后续需要专门研究：

- 倾诉、陪伴、共同思考模式的命名与 UI 表达。
- 用户说话风格与回复策略之间的映射。
- 高情绪表达的风险分级。
- 心理调节流程在 AI 对话中的安全应用。
- 工作模式与非工作模式之间的平滑切换。
